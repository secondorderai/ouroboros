01 · Prompt Engineering

Make intent
executable.

Prompt engineering defines how the model should reason, choose tools, and communicate. Ouroboros builds a structured system prompt from the current runtime state—not a single, unchanging instruction.

How Ouroboros handles it

  1. Start with stable behavior. ReAct instructions, output conventions, and the five-tier permission model form the base.
  2. Compose optional sections. Response format, active mode, tools, skill catalog, active skill, memory, AGENTS.md, and RSI guidance are added when present.
  3. Disclose skills progressively. A name and description enter the catalog; full instructions load when activated. AGENTS.md files stack root-first from cwd ancestors.
Important boundary: an instruction to stay safe is not enforcement. The harness must independently validate and authorize the action.
Source, knobs & common mistake

Change task wording, AGENTS.md, skill instructions, and mode overlays. The prompt is rebuilt before model calls to reflect changing state. Tool schemas normally travel as native tool definitions; the catalog in the prompt is not the schema validator.

Avoid: adding more prose to compensate for missing tools, evidence, or runtime controls. This lab shows abbreviated sample sections, not the full production prompt.

02 · Context Engineering

Supply the right state.
Preserve what matters.

Context engineering controls what information is available for the next decision. Ouroboros separates reusable knowledge from active task state and raw conversation history.

How Ouroboros handles it

  1. Load budgeted memory layers. Durable MEMORY.md, a session checkpoint, and recent daily working memory have independent budgets.
  2. Track context pressure. Estimates include instructions, memory, conversation, and tool results. Default thresholds warn at 70%, flush at 80%, and compact at 90%.
  3. Externalize before trimming. Capture observations and refresh the checkpoint before normal compaction; retain a recent history tail. Provider length errors also have a recovery path.
Prompt vs context: prompts prescribe behavior. Context supplies facts, prior decisions, constraints, and open loops needed to apply that behavior.
Source, knobs & common mistake

Configure model context capacity, thresholds, memory budgets, and tail length. Defaults are 1,500 / 1,200 / 1,000 estimated tokens for durable / checkpoint / working memory, with 12 recent messages retained by the normal compactor.

Checkpoint packing prioritizes next steps, constraints, and open loops. Estimates are not exact provider token counts. Normal compaction is gated on successful checkpoint refresh; emergency length recovery is a distinct path.

Avoid: treating the full transcript as the only memory, or deleting old history before active state is preserved.

03 · Agent Harness Engineering

Turn proposed actions
into governed actions.

The harness is the runtime around the model: tool contracts, authorization, execution, cancellation, and observability. It makes agent behavior more explicit and inspectable.

How Ouroboros handles it

  1. Validate typed tool calls. Zod schemas reject invalid arguments before approval. Tool results return structured success or error observations.
  2. Constrain execution. Tool tiers, configured permissions, Plan mode, child-agent registries, and permission leases narrow the allowed actions.
  3. Isolate and observe. Low-tier shell/code children use an OS sandbox when available. Filesystem/network restrictions, approval queues, events, and logs expose what happened.
Architecture: the CLI owns agent intelligence. Electron is a presentation layer connected through typed preload APIs and JSON-RPC over NDJSON.
Source, knobs & common mistake

The model can propose; it cannot grant itself a permission. Actual tool definitions determine tiers. The memory tool is tier 3; generated-skill creation is tier 2; a sandbox bypass resolves to tier 4.

Sandbox restrictions described here apply to shell/code child processes, not a claim that every tool or host operation is sandboxed. Protected skill/memory/config paths are denied to those sandboxed children. A violation can request approval for an unsandboxed tier-4 retry.

Avoid: confusing a prompt's safety prose with an authorization check, or assuming a write-tool filename alone selects its tier. This is a deliberately simplified policy demo, not a complete security emulator.

04 · Agent Evals Engineering

Judge evidence.
Not confidence.

Evaluation asks whether the work satisfies the task. Ouroboros combines a runtime completion verifier with software regression tests, generated-skill self-tests, and separate benchmark harnesses.

How Ouroboros handles it

  1. Extract a done contract. A fresh-context call derives checkable outcomes from the task and user steering; configured standing criteria are appended.
  2. Judge tool-result evidence. The verifier receives the task, criteria, candidate answer, and a capped evidence ledger independent of history compaction. Claims are not evidence; verdicts are pass, fail, or unknown.
  3. Feed failures back. Unmet criteria can trigger bounded ReAct retries. Defaults gate long primary-agent tasks at 5 tool calls with up to 2 verifier-driven retries.
Not a guarantee: unknown or verifier errors can be accepted with warnings. Exhausted/repeated failures may escalate to a human override or return an answer with unmet-criteria warnings.
Source, evaluation layers & limits

Triggers are always / long-tasks / off, but zero-tool answers and subagents bypass this completion gate. Step-limit handoffs are intentionally incomplete and are not gated.

When an approval handler exists, exhausted or identical repeated failures may request a tier-4 completion override once per run. Approval accepts with a warning; denial grants one extra retry batch. Subsequent exhaustion can still return unmet-criteria warnings.

  • Regression tests: deterministic Bun unit/integration tests and desktop Playwright flows.
  • Skill tests: generated scripts are validated and run; passing does not prove generalization or transactional safety. Generated files can already exist when tests fail.
  • Benchmarks: ARC-AGI-3 and a Terminal-Bench pilot exist separately. No leaderboard performance is claimed here.

Avoid: treating an LLM judge as an objective proof, equating one passing task with broad reliability, or hiding unknown/failure states. This lab is deterministic teaching logic, not a live LLM judgment.

05 · Loop Engineering

Improve the next action.
Then the next task.

Loop engineering determines how an agent uses feedback, when it stops, and what experience survives. Ouroboros has a task-time control loop and a separate, longer-lived learning lifecycle.

How Ouroboros handles it

  1. Close the task loop. Plan, call tools, observe results, and iterate. Each model step can use updated context. Cancellation, steering, provider recovery, and step budgets constrain the run.
  2. Externalize experience. Observations and structured checkpoints preserve constraints, decisions, open loops, and a next best step.
  3. Reuse qualified patterns. Configured post-task reflection may lead to skill generation, validation, and tests. Dream consolidation merges memory; future prompts and activated skills can use that experience.
Two timescales: ReAct improves progress within a task. RSI can improve reusable instructions and memory across tasks. Neither means the model's weights are being trained.
Source, stop conditions & limits

Default step budgets vary by entrypoint (desktop/interactive 200, single-shot 50). Reaching the budget produces an incomplete handoff rather than a successful-completion claim.

Auto-reflection and novelty/generalizability gates are configurable. The threshold helper uses strict greater-than comparisons (default 0.7), not a promise that every run yields a skill. Observation-backed repeated-pattern proposals also exist.

Default session-end dream uses consolidate-only; full/propose modes are separate. RSI errors are isolated from the user's task, and evolution events provide an audit trail. A test-failed generated skill is reported; do not assume automatic file rollback or guaranteed safe future discovery.

Avoid: endless retries, learning from unsupported claims, or calling every feedback loop “training.”
